# 05. ページングとメモリ

## アドレスには二つの意味がある

ページングを使うと、仮想空間の連続した範囲を物理メモリの離れた領域へ対応づけられます。アクセス権もページ単位で管理できます。カーネルが物理メモリの配置に縛られずに動き、無効なアクセスを検出できる理由を追うため、まず二種類のアドレスを分けます。[17]

ソースコードに現れるポインタの値を、そのままRAM上の位置だと考えてはいけません。仮想アドレスはCPUが命令実行時に使うアドレスで、物理アドレスはメモリ装置上の位置です。ページングは仮想アドレスを固定サイズのページ単位で物理フレームへ対応づける仕組みです。ページは仮想空間側の単位、フレームは物理メモリ側の単位と考えると区別しやすくなります。[17]

CPUはページテーブルをたどって仮想アドレスを変換します。x86_64では複数段のテーブルを使いますが、段数やビット分割はCPUモード・アーキテクチャに関する仕様です。概念図では、上位の表が次の表を指し、最後の項目が物理フレームとアクセス権を示します。[17][18]

各テーブルは全仮想アドレス空間を一枚の巨大な表で覆うのでなく、必要な範囲を段階的に記述します。これによって未使用の大部分の空間に対して、末端の表をすべて用意せずに済みます。変換の結果はCPU内部のTLB（Translation Lookaside Buffer）にもキャッシュされ、毎回テーブルを最初から読む負担を減らします。ページテーブルを書き換えた後にTLBの更新が必要となる規則はアーキテクチャ依存なので、変更APIやCPU仕様に従います。[17][18]

次の図は、仕組みを追うための四段テーブルの例です。実際の段数や設定は対象のCPUとページングモードで確認します。[17][18]

```mermaid
flowchart LR
    V[仮想アドレス] --> T1[ページテーブル段1]
    T1 --> T2[ページテーブル段2]
    T2 --> T3[ページテーブル段3]
    T3 --> T4[最終段: フレームと権限]
    T4 --> P[物理フレーム + ページ内オフセット]
```

ページサイズを4 KiBと仮定する説明例なら、仮想アドレス `0x12345` はページ番号 `0x12` とページ内オフセット `0x345` に分けられます。ページテーブルがページ番号 `0x12` を物理フレーム `0x8A` に対応づけるなら、物理アドレスは `0x8A000 + 0x345 = 0x8A345` です。これは計算例であり、実際のページサイズやテーブル構成はCPUと設定を確認してください。

割り算の商が仮想ページ番号、余りがページ内オフセットです。ページテーブルは商を物理フレーム番号へ置き換え、余りは物理アドレスの下位部分として保ちます。ページサイズを`P`とすれば、`page = address / P`、`offset = address % P`です。

## なぜ間接変換するのか

ページテーブルの権限は、読み取り・書き込み・実行を制御し、存在しない領域や禁止されたアクセスをページフォルトとして検出する手段になります。アドレス空間を分ける設計では、無関係な領域への誤書き込みを防げます。ただし権限設定を誤ると、必要なコードが実行できないなど別の障害が起きます。[17][18]

変換の権限は、ページテーブルの各段に記録される属性の組み合わせとして働く場合があります。そのため最終段の項目だけを見て「書き込み可能」と断定できないことがあります。また、ページサイズを大きくするとテーブル管理が効率化する場合がある一方、細かな権限分離や小領域の利用では無駄が生じます。ページサイズや巨大ページの有効条件は、教材の計算例と実機の状態を区別してください。

ブートローダはカーネルを起動するためのページテーブルを用意しますが、どの範囲がどの仮想アドレスへ対応するかは設定に依存します。BootInfoの `physical_memory_offset` は、物理メモリ全体が仮想空間のどこから見えるかを示す情報として提供される場合があります。この値が存在しても、すべての物理アドレスへの参照が安全になるわけではありません。BootInfoのメモリマップで利用可能とされた範囲だけを適切に扱い、同じ物理フレームを別の仮想アドレスから誤って同時に参照する危険にも注意します。[22]

## ページテーブルとメモリマップを混同しない

メモリマップは物理領域の用途を知らせる地図であり、ページテーブルは仮想アドレスから物理フレームへの変換表です。前者が「RAMのどこを使ってよいか」を示し、後者が「この仮想番地のアクセスをどこへ通すか」を制御します。usableな領域であっても、ページテーブルにマップされていなければCPUから直接読み書きできるとは限りません。逆にマップ済みでも、その領域をカーネルが再利用してよいとは限りません。

CR3はx86_64で現在のページテーブル階層の起点をCPUへ示すレジスタです。CR3が指す変換構造やTLBの更新規則はページング実装の資料で確認します。[18]

BootInfoの物理メモリマップは領域の用途情報です。ページテーブルとTLBとは役割が異なり、どれか一つを調べただけではメモリの所有状態まで分かりません。[22]

この違いは、アドレス変換の図と物理範囲の図を別々に描くと整理できます。前者では仮想ページ、物理フレーム、権限を線で結び、後者では物理アドレス範囲を用途ごとに色分けします。仮想アドレスから物理フレームへ線が引けても、そのフレームが空きであることを意味しません。逆に空きフレームを見つけても、仮想側に割り当ててアクセス権を設定するまでは使えるメモリ領域になりません。アロケータを作るとき、この二つを接続する手順が必要です。

ページフォルトはデバッグに有用な情報を含みます。アクセスしようとした仮想アドレス、読み書き・実行の種別、特権レベルなどを確認すれば、無効ポインタ、権限違反、未マップ領域を区別する手掛かりになります。例外ハンドラが整っていると、この章の知識を実際の障害解析に結びつけられます。[17][18]

Phil Oppのページング導入と実装記事は、ページテーブルの考え方を深める補助資料です。[17][18] APIやブート時のマッピングは現在のbootloaderの版と設定に合わせて読み替えます。ページテーブルを自前で変更する前に、既存のマップを調べ、変更がコード・スタック・装置マッピングのどれに影響するかを確認しましょう。

## 手を動かす・確認する

**概念演習（紙上で実施）:** 上の4 KiB計算例を繰り返し、仮想アドレス`0x12345`をページ`0x12`とオフセット`0x345`に分けてください。ページ`0x12`がフレーム`0x8A`に対応する場合、物理アドレスは`0x8A000 + 0x345 = 0x8A345`です。合格条件は、ページ・オフセット・フレーム・物理アドレスの計算がすべて一致することです。

**任意のカーネル統合:** 起動可能なx86_64カーネルの土台と、現在のページテーブルを読み取り専用で調べる機構が必要です。選んだ仮想ページについてページ・フレーム・オフセット・有効な権限を報告し、整合することを確認します。合格条件は変換と権限の報告が一貫していることです。マップは変更しません。

仮想アドレスから物理アドレスへの変換と、その物理フレームを使う権利は別々に確認します。ページテーブルで変換できても領域が空きとは限らず、空き領域でもマッピング前はアクセスできません。次章では、空きフレームをページ単位で管理した上で、小さな可変長領域を貸し出すヒープアロケータを組み立てます。
