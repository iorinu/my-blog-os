# UEFI環境でVGA風の文字表示に戻せるか

## 結論

**UEFI対応を維持したまま、以前のVGAテキストモードに近い表示と出力方法を実装できます。**

ただし、以前のように文字セルのメモリー領域`0xb8000`へ直接書き込む方法は使いません。UEFIではブートローダーから渡されるFramebuffer（画面のピクセル領域）に、カーネルが文字をピクセルとして描画します。表示を担当する部分をFramebuffer向けに置き換えれば、`print!`／`println!`で文字を出す構造や、80列×25行・文字色・スクロールといった見た目は再現できます。

## コミット履歴から分かる変更

| コミット | 表示・起動方法 |
| --- | --- |
| `a6b6eb2` `VGAテキストモードまで` | BIOS向けのVGAテキストバッファを実装。80列×25行の文字セルへ、文字コードと色属性を書き込む。 |
| `2f41f22` `Migrate boot flow to UEFI bootloader` | `bootloader 0.11`を使うUEFI起動へ移行。VGA用コードは残ったが、UEFIカーネルからは呼び出されていない。 |
| `2b673b6` `Add framebuffer Hello World output` | 起動情報からFramebufferを受け取り、固定の`Hello World!`をピクセル描画する処理を追加。 |
| `ec93036` `Render ASCII output through framebuffer writer` | Framebufferを`fmt::Write`の出力先にし、`print!`／`println!`相当の文字出力を追加。VGA用コードを削除。 |

コミット履歴だけでは、個々の変更にAIを使ったかどうかまでは確認できません。ここでは履歴に残っているコードと変更内容を比較しています。

## 以前のVGA表示

`a6b6eb2`の`src/vga_buffer.rs`では、画面を80列×25行のセルとして扱っていました。各セルには文字と色属性があり、VGAがその値を文字として画面に表示します。

- 画面メモリーのアドレスは`0xb8000`。
- 文字色は赤、背景色はシアン。
- `print!`／`println!`から`core::fmt::Write`を通して出力。
- 行末では画面を上へスクロール。
- 文字列はASCIIを前提とし、それ以外のバイトは代替文字に置き換える。

この方式では、カーネルが文字の形をピクセルへ変換する必要はありません。VGAハードウェアが文字コードと属性を読み、内蔵フォントを使って表示します。

## 現在のFramebuffer表示

現在の`kernel/src/framebuffer.rs`は、UEFIブートローダーから渡されたFramebufferへ文字のドットを直接描きます。

- `font8x8`の8×8フォントを4倍に拡大し、1文字をおよそ32×32ピクセルで表示。
- 文字色は白、背景は黒。
- 左上から出力し、画面幅に合わせて折り返し、下端ではピクセル領域を上へスクロール。
- 現在はASCIIを対象とし、ASCII以外は`?`に置き換える。
- `FrameBufferInfo`の幅・高さ・ピクセル形式・行のstrideを使ってピクセルを書き込む。

このため、以前の「小さな文字が並ぶ文字端末」ではなく、「大きなドット文字をFramebufferへ直接描画する画面」になっています。さらに、`src/main.rs`のQEMU起動引数は`-display none`なので、現在の`cargo run`では画面を表示せず、シリアル出力だけを確認する設定です。

## なぜUEFIでは実装方法が変わるのか

`0xb8000`は従来のVGAテキストモードに依存する領域です。UEFI起動では、画面出力にGOP（Graphics Output Protocol）が使われ、カーネルはピクセル形式のFramebufferを受け取ります。UEFI専用の実機でVGAテキストメモリーが利用できる保証はないため、以前の`0xb8000`書き込みをそのまま戻すのは適切ではありません。

UEFIのブートサービスが提供するテキストコンソールを使う案もありますが、カーネルが動き始めた後の通常の画面出力としては使えません。現在の構成では、Framebuffer上に文字を描く方式が適しています。

## 推奨する実装方針

現在のUEFI起動経路とFramebufferを保ち、Framebuffer出力Writerを「ピクセル端末」から「文字セル端末」へ変更します。

1. **80列×25行の論理セルを用意する。** 各セルは文字と色属性を持ち、以前の`ScreenChar`に近い構造にする。
2. **文字セルをFramebufferへ描画する。** 既存の8×8フォントを縦方向に2倍にして8×16ピクセルのセルにすると、80×25セルで640×400ピクセルを使う。一般的な画面サイズより小さいFramebufferでは、幅・高さから列数と行数を減らす。
3. **色属性をRGBへ変換する。** VGAの16色をRGB値へ対応付け、文字ごとの前景色・背景色として描画する。初期値は以前のコードに合わせて赤文字・シアン背景にできる。
4. **文字の位置とスクロールはセル単位で管理する。** 改行で次の行へ進み、最終行を超えたらセルの行を上へ移動してから再描画する。Framebufferは解像度やstrideが異なるため、列番号から単純に連続メモリー上の位置を計算せず、既存のピクセル書き込み処理を利用する。
5. **`print!`／`println!`とシリアル出力を分けて維持する。** 画面出力の見た目を変えても、フォーマット文字列を出す呼び出し側はほぼそのまま使える。シリアル出力は障害調査用として残す。

元コードの初期カーソル位置は最下行で、改行時にスクロールする設計です。まずはその動作まで再現できますが、起動メッセージを左上から表示する一般的な端末動作にするかは実装時に決める点です。どちらもFramebuffer上で実現できます。

## 制約と確認方法

- 実際の解像度はUEFIファームウェアが選んだGOPモードに依存する。80×25セルをすべて表示するには、少なくとも640×400ピクセル必要。
- VGAの色はFramebufferのRGB色へ変換して近似する。表示装置やファームウェアによって、色味は完全には一致しない。
- 日本語を表示するには、ASCIIフォントとは別に日本語フォントとUTF-8の文字処理が必要。最初の段階では、以前のコードと同様にASCIIのみを対象にできる。
- 視覚確認にはFramebufferが見える実行環境が必要。現状の`cargo run`はQEMUの画面を非表示にしているため、QEMUの画面を表示する起動方法を用意するか、実機で確認する。
- 描画時はFramebufferのピクセル形式とstrideを尊重する。画面幅だけを使った計算では、環境によって文字が崩れる可能性がある。

## 判断

変更可能なのは「文字の見た目と端末の振る舞い」であり、表示の土台はVGAテキストメモリーからUEFI Framebufferに変わります。UEFI専用の実機を対象にするなら、現在のFramebuffer Writerを80×25の文字セル端末として再設計するのが、当初の表示に近づけつつ起動方式との互換性を保つ案です。
